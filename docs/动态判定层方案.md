# 动态判定层方案（轨迹 / 晃动）

> 2026-09-30 起草。本文是设计方案，不是实施完成证明。文中所有阈值参数均为 UNVERIFIED 初值，与 `passState.js` 现有参数的纪律一致：标注 UNVERIFIED，不宣称实验结论。

## 1. 背景与目标

当前判定管线只核**静态手型**：单帧几何（`evaluate`）→ 质量门 + 内容门（`judge`）→ 连续保持（`passState`）。GF 0021—2019 中带动态成分的字母**经 2026-10-01 官方文字直读确认后只剩 ê 与 ü**（J=食指回勾、Z=食小指横伸，均为静态指式；书空仅用于 4.4 声调/隔音符号）：

| 字母 | 规范动态成分（原文文字直读） | 现状 | 加动态层后 |
|---|---|---|---|
| ê | 「用 E 的指式，手上下晃动两下」（4.3） | `demo_only`（与 E 静态不可区分） | 具备与 E 区分的判定能力 |
| ü | 「用 U 的指式，食、中、无名、小指前后晃动两下」（4.3） | `pending_review`（U 裁定后手型已转写，升格待掌心朝向能力） | 具备能力，升格仍依赖人工流程 |

> 存档：2026-09-30 初版方案曾把 J/Z 列为动态字母（画钩/画 Z），并已落地 J/Z 的 trace 判定；2026-10-01 转写后确认系对 OCR 文字「（顺势画钩）」「（并顺势画出 Z 形）」的误信——那些括号内容是 OCR 污染，原文无此句。相关 trace 代码保留在 motion.js 中备用（未被任何 letters.json 条目引用）。

## 2. 非目标

- 不解决 M/N/S（遮挡关系问题，单摄像头原理性受限，另行可行性实验）。
- 不修改 `evaluate.js` 的任何静态几何阈值与判定逻辑。
- 不改变 `practiceStatus` 四档语义、不引入运行时可升格路径。
- 不引入新导出格式、不引入独立第三方识别器（如现成手势库）。
- 不做声调符号（规范另有四个声调手势，letters.json 未收录，不在本期）。

## 3. 总体设计：加一层，不改内核

```
摄像头帧
  └─ judge(input, hold, motion)          ← 编排层，加第三态
       ├─ assessInputQuality             ← 不动
       ├─ evaluate（单帧静态几何）        ← 不动
       ├─ passState（静态保持门）         ← 不动
       └─ motion.js（新增，纯函数模块）   ← 动态判定层
```

设计原则与现有代码一致：

- **纯函数、无 DOM、无 MediaPipe**：`motion.js` 只消费 `{x, y}` 点列与时间戳，可离线测。
- **时间戳纪律照搬 `passState`**：`videoTime`/`nowMs` 必须有限、非负、单调不减；同一 `videoTime` 不双计；`gap > maxGapMs` 清空缓冲（先过期后去重，顺序与 `observePass` 一致）。
- **镜像纪律不变**：DISPLAY 镜像仅影响展示，motion 用原始 landmarks，不做反射。
- **阈值全部 UNVERIFIED**：写进常量并注释，不宣称标定。

## 4. 判定流程（状态机）

带 `rules.motion` 的字母，判定从“保持即过”变为两阶段：

```
idle
  │ 静态手型 pass（evaluate 通过）
  ▼
pose_ok ──静态断──▶ idle（静态 fail 照旧给 issues 提示）
  │ 进入动态收集窗口（MOTION_WINDOW_MS，初值 3000，UNVERIFIED）
  ▼
collecting ──轨迹/晃动匹配成功──▶ pass
  │ 窗口超时 / 静态手型中途破坏 / 时间戳违规
  ▼
fail（提示语区分：手型对但没做动作 / 动作方向不对 / 动作次数不够）
```

关键决策：

- **静态是动态的前置门**。手型不对时不收集轨迹，避免用户乱挥被判“动作对”。
- **动态判定期间放宽保持门**：做动作时手不可能静止，J/Z/ê/ü 的 `hold` 语义从“连续 6 帧静态”改为“静态命中即进入动态窗口”。`passState` 不改代码，只是动态字母不走 `holdReady` 分支。
- **pass 语义变更需总控确认**：J/Z 目前是 `pose_practice`，现在 pass=“静态对”；上线动态层后 pass=“静态+轨迹对”。这是判定口径收紧，属内容层决策，代码只提供能力，默认是否启用见 §8 分阶段。
- **自测模式（mode=test）同步更新**：`practiceSession.testScopeText` 与 `letterLibrary.isStaticOnlyLetter`（目前硬编码 J/Z 两个 id）改为读 `rules.motion` 是否存在，消除硬编码。

## 5. 内容层：rules.motion 规则词汇

`letters.json` 仍是唯一事实来源。在 `rules` 下新增一个键，词汇最小化：

```jsonc
// GF0021.J —— 小指画钩
"motion": { "kind": "trace", "finger": "pinky", "path": "hook" }
// GF0021.Z —— 食指画 Z
"motion": { "kind": "trace", "finger": "index", "path": "z" }
// GF0021.EH（ê）—— 整手上下晃动两下
"motion": { "kind": "shake", "part": "hand", "axis": "vertical", "cycles": 2 }
// GF0021.UE（ü）—— 手指前后晃动两下
"motion": { "kind": "shake", "part": "fingers", "axis": "forward", "cycles": 2 }
```

- `evaluate.js` 的 `KNOWN_RULE_KEYS` 增加 `"motion"`，但 `evaluate` 本体**忽略**该键（它是时序规则，不属于单帧几何）。这样含 motion 的内容不会被 `inspectRules` 判 `unsupported` 而 blocked。
- 轨迹的**方向语义必须对照规范原图确认**（钩朝哪边收、Z 的起笔与走向、左右手镜像时方向如何变换——规范 5.1 说用左手时“方向作相应改变”）。这些写进规则前属于 `docs/内容核定表.md` 的人工核对项，方案不预设结论。

## 6. 识别算法（motion.js）

### 6.1 采样缓冲

- 每帧记录追踪点：`trace` 取规则指定指尖（J→lm[20]，Z→lm[8]）；`shake(hand)` 取掌心（lm[0] 与 lm[9] 中点）；`shake(fingers)` 取伸直各指尖的集合。
- 坐标用手尺度归一（除以 `handScale`，复用 `evaluate.js` 已导出的函数），消除远近影响。
- 缓冲按时间窗淘汰（只保留最近 `MOTION_WINDOW_MS`），同一 `videoTime` 去重，gap 超时清空。

### 6.2 trace（画钩 / 画 Z）：方向序列匹配

不用点云重采样（$1 recognizer 类）——参数多、难解释。用**方向段序列**匹配：

1. 把轨迹点列按最小位移（`MIN_STEP`，手尺度单位，UNVERIFIED）抽稀；
2. 每段量化为 8 方向；
3. 对方向序列做游程压缩（连续同向合并），得到方向串；
4. 与目标模式比对：
   - `z`：`右 → 左下（斜）→ 右` 三段结构（观看者视角，左右手镜像时镜像处理）；
   - `hook`：`下 → 下弯弧`（先下行再向内勾），具体收拢方向待对图确认；
5. 允许段内有少量噪声方向（容忍度参数 UNVERIFIED）。

输出 `{ matched, progress, reason }`，`reason` 用于给用户可解释的提示（“方向反了”“只画了一半”）。

### 6.3 shake（晃动）：振荡检测

- `vertical`（ê）：掌心 y 序列找符号交替的速度过零点，数完整振荡周期；要求 ≥ `cycles` 个周期、振幅 ≥ `MIN_AMPLITUDE`（手尺度单位，UNVERIFIED）、且不振出画面（质量门已管出框）。
- `forward`（ü，**最高风险项**）：前后晃动在图像平面几乎不可见，候选信号有两个——
  1. MediaPipe 的 z 通道（相对腕部，噪声大）；
  2. 手指“前后晃”在动作上常表现为弯曲/伸展的往复，可用 `fingerCurlDeg` 的时序振荡检测，复用现有 curl 几何。
  
  两条路都必须先过**实机可行性验证**（§8 阶段 0），验证不过则 ü 维持 `pending_review`（它本来也依赖 U 裁定，不阻塞本期其余三个字母）。

### 6.4 模块接口（草案）

```js
export function createMotionState(opts)   // 类 createHold；带窗口、缓冲、时间戳游标
export function resetMotion(state)
export function observeSample(state, { lm, geom, videoTime, nowMs, spec })
export function matchMotion(state, spec)  // → { matched, progress, reason }
export function motionView(state)         // 透出阈值供离线统计，同 holdView 纪律
```

`judge` 编排：质量门 → 静态 evaluate → 无 `rules.motion` 走原 hold 路径（现行为完全不变）；有 `rules.motion` 走 §4 状态机。`presentJudge`/`presentTestJudge` 增加动态态的文案（“手型对了，现在画一个钩”“方向反了”等）。

## 7. 测试计划

项目已有测试基线，新增与回归如下：

- **新 `practice/src/motion.test.js`**：合成轨迹/振荡序列（正例、反方向、半段、次数不足、超时、videoTime 重复不双计、gap 清空、非有限时间戳拒绝）。合成 golden 只做规则回归，不等于国标或真实检测通过——沿用 `pose-goldens.test.js` 的声明纪律。
- **回归**：`evaluate.test.js`、`reliability.test.js`、`pose-goldens.test.js` 必须全绿；`judge` 对无 motion 字母的行为逐一不变（reliability 套件覆盖）。
- **提交门槛**：按 AGENTS.md，每次提交前跑三条测试命令。

## 9. 风险与开放问题

1. **轨迹方向语义未对图**（钩的收拢方向、Z 走向、左右手镜像规则）——列入 `docs/内容核定表.md` 人工核对清单，代码把方向做成规则数据而非硬编码，便于核定后修正。
2. **ü 前后晃动的可检测性**——单摄像头原理性弱点，阶段 0 一票否决。
3. **pass 口径收紧**对已有练习记录的影响：J/Z 老记录是“静态通过”口径，上线后语义不同，`progress.js` 记录不 retroactive 改写，需在界面对这两个字母说明判定口径已升级。
4. **阈值全部 UNVERIFIED**：窗口时长、最小位移、振幅、周期数容差都需要真实样本标定后才可去掉 UNVERIFIED 标记，流程同现有 `passFrames`/`maxGapMs`。
